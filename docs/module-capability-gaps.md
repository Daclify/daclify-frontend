# Module capabilities and gaps — 14 October 2026

This review compares the current producer contracts, public SDK/API, frontend controls and explanatory help. It describes code capabilities, not a claim that every external provider or real-money flow was exercised in this session. Sources: core protocol 0.15.0-alpha.22, modules 0.10.0-alpha.31, frontend 0.15.0-alpha.34. Existing authorization, accounting and liability rules remain authoritative.

## What is possible now

| Module or flow | Existing capability | Gap or restriction | Kind |
| --- | --- | --- | --- |
| Decide ordinary ballots | Member, credit or deposited-stake weight; saved quorum/duration/approval policy; one selection per eligible member; finalization. This update adds an explanation, a pinned supporting-document link, custom 3–16-choice polls and actual choice/tally/result display. | Neutral two-choice polls are unavailable: the contract reserves choice 0 for rejection and choice 1 for approval. A custom poll requires the leading choice to reach the DAO's majority approval threshold; plurality alone can fail. No ordinary-ballot abstention, revoting, ranked or secret voting. | Contract semantics |
| Elections and executive terms | Rules-document versions, nominations, candidate selection, bounded seats/terms, recall, optional executive roster handover. | Election titles include a reserved `Executives` meaning. Handover still needs successor pairing/synchronization; election success alone does not activate authority. Forms and lists mostly display document labels/references rather than opening the exact rules/evidence version in context. | Contract workflow and UI discoverability |
| Governing documents | Register official documents; propose amendments; member vote or configured adoption; exact version commitments; acceptance records and history. | This is the strongest existing in-context document-review flow. General ballots/elections/Works/Grants should reuse the same review experience. Replacing a document does not silently replace the version already adopted or accepted. | Reusable UI pattern |
| Works | Propose up to sixteen funded milestones; contributor submission; independent review/revision; bounded funding votes; cancellation preserving approved claims; payment settlement. | No dispute/arbitration process. A scope change needs a successor project rather than rewriting funded terms. Proposal/submission/review references are visible but are not consistently linked to an exact document reader from each card. | Contract capability and UI |
| Contribution agreements and services | Offer an agreement with exact document, contributor, milestone amounts/dates and term; designated contributor accepts; separate funding approval. Member service offers are read from validated published documents. | No offer-creation form inside the service catalogue; authoring the structured offer currently requires the document workflow. No agreement amendment/renewal workflow; changed terms need a new proposal and fresh consent. | Missing authoring UI and contract limits |
| Payroll | Fully funded native-token terms of 1–12 installments; future start and bounded interval; one-off payment via one installment; editable label/pause; manual catch-up settlement; claims survive module removal. | Label is edited after commitment. There is no payroll terms-document reference or renewal action. A schedule pause stops its helper, not direct Treasury settlement of already approved obligations. Contract limits are fixed; installing a preset does not create arbitrary new limits. | UX and contract limits |
| Grants rounds | Rules and deadlines; application and amendment; independent eligibility review; revision-bound award votes; award execution into Works; closing applications/rounds. | The advertised cap reserves no money. Matching funds/donor pots are absent. Amendments invalidate older review/vote commitments. As with Works, proposal/review documents need more consistent in-context viewing. | Contract capability and UI |
| Endorsement admission | Revision-bound applications; distinct eligible witnesses; withdrawal of witness support; reviewed admission under the DAO policy. | Endorsement eligibility and threshold are DAO admission policy, not a freely editable form field. Document/version references are shown, but applicants/reviewers need clearer direct access to the exact application evidence. No independent-human or anti-collusion proof is supplied by distinct member keys. | UI and identity-policy limit |
| Community Activity / connected mini apps | Scoped app registration/consent; activity receipts; independent reviews; source-revision links to advisory decisions; encrypted app-key epochs and grants. | Receipt/review records do not prove the real-world task happened. App-specific evidence rendering stays the app's responsibility. Mini-app database hosting and an automatically generated operational app are not supplied by the connection itself. Decisions are advisory and do not create a payment obligation. | Integration boundary |
| External Telos governance | Separate network ballots, Foundation/all elections and producer voting; actual publisher/options/totals/period; native-wallet signature and live-rule checks. | This is external Telos authority, not a Daclify member ballot. It requires the supported native account and its eligible network weight. Missing retained records or unsupported ballot types cannot be reconstructed or voted on by inventing options. | External-chain boundary |
| Connected payment adapters | Explicit supported rails; scoped intents and receipt/reconciliation paths; authorized withdrawal/settlement. | A DAO proposal is not a payment-provider integration. Provider qualification, funding, finality and reconciliation remain rail-specific. Do not advertise generic fiat/crypto payouts from the presence of a module card. | Provider qualification |
| Archive and retention | Bounded supported-family export/archive flows; commitments and verification; approved obligations and protected decision families are preserved. | This operator's automatic deletion can be disabled. An informational document ID in arbitrary ballot metadata is not a registered archival dependency. Long-lived supporting material needs an explicit retention choice; a link alone does not guarantee retrieval. | Storage policy and contract dependency |

## Prioritized follow-up

1. **Decision integrity:** implement the existing [ballot-integrity plan](../../daclify-backend-core/docs/superpowers/plans/2026-10-08-ballot-integrity.md). Current vote actions bind the numeric selection, member and DAO, but do not carry a contract-checked commitment to the definition shown by the API. Correct UI rendering does not replace that upgrade. Older cached frontend builds also hardcode binary labels, so users must reload the current interface before viewing or voting on custom polls. Preserve legacy votes and typed funding/election semantics.
2. **Exact document review across modules:** reuse governing-document review/integrity/decryption for elections, Works, Grants and admission, including pinned versions and a return path. This update supplies exact version/commitment navigation for ballot attachments; it does not claim those other cards are fixed.
3. **Service-offer authoring:** provide a small form using the existing producer-owned `ServiceOfferDocumentSchema`, rather than asking ordinary members to compose JSON.
4. **Payroll and Works product decisions:** decide whether payroll needs contract-bound terms/renewals and whether Works needs arbitration. These require policy and contract design; cosmetic inputs would not implement them.
5. **Neutral two-choice and richer voting:** introduce an explicit ballot subtype before adding neutral two-option, abstention, approval/ranked or revoting controls. Preserve existing binary outcomes and funding authority.
