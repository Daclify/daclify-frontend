# Explicit whole-token work payments

The user rejected the one-payment-per-line textarea as too easy to misunderstand and requested full TLOS amounts. The fix uses one row for each milestone with a blank, labelled whole-token amount, an optional due date and an explicit Remove button. Add milestone adds an empty row and stops at 16. A visible total and an acknowledgement precede submission; changing any proposal payment/reference/date or contributor clears the acknowledgement. This prevents formatting, precision and stale-confirmation errors; it cannot determine whether an intentionally entered amount matches the user’s intentions.

The UI correction does not change the Works action ABI or backend contracts. It was initially tested as frontend 0.14.0-alpha.15, then integrated with current dev as frontend 0.15.0-alpha.8. UI amounts are positive whole units of the DAO’s treasury token and serialize at its exact native precision. No floats, silent rounding, exponent notation, grouping, signed amounts or automatic payment defaults are used. Both individual amounts and the aggregate must fit Antelope `asset::max_amount`; the published core `records.hpp` bounds `add_amount` by that same maximum. Milestone dates travel with their corresponding amounts in row order, and dates outside the action’s uint32 range cannot submit. Existing contributor/document choices, signer/grant/code checks, consent, funding and settlement behavior remain authoritative.

The existing shared textarea state was also used by Payroll. Payroll now keeps its own unchanged amount field so work row edits and successful proposal resets cannot change a payroll draft. Cancellation and failed submissions preserve rows, dates and acknowledgement; confirmed success resets to one empty row. DAO/account changes clear scoped drafts. All editing, add/remove and closing controls are disabled while the relay is pending.

Regression tests were written before the implementation: the initial browser check failed because the individual milestone amount fields were absent. Unit cases cover whole-token conversion, invalid syntax and precision, empty/overlong row lists, individual/aggregate overflow and totals beyond Number’s safe integer range. Browser cases cover add/remove fidelity, empty defaults, totals, invalid values, acknowledgement invalidation, limits, signed amount/date encoding, retry and pending state. Existing paid/native test callers were updated to explicitly enter and acknowledge an amount.
